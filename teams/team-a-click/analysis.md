## 1. 한 줄 요약: 무엇을 측정하는가

CLIcK은 한국의 시험·교재를 바탕으로 구성한 **1,995개 객관식 문항으로 한국 문화 지식과 한국어 이해 능력을 평가하는 벤치마크**다. ([논문][paper])

KMMLU는 45개 과목의 전문 지식과 문제 해결 능력을 폭넓게 평가하고, CLIcK은 한국 사회·문화와 독해·문법·언어 사용에 초점을 둔다. CLIcK은 이를 문화 8개 분야와 언어 3개 분야로 나누어 평가한다. ([KMMLU 분석](../team-a-kmmlu/analysis.md), [CLIcK 분야 구성][author-readme])

### 구성과 구축 과정

- **HF ID**: `EunsuKim/CLIcK`.
- **기본 config / split**: `default` / `train` 하나다. 이 `train`이라는 이름과 벤치마크의 평가 용도를 구분해야 한다. 별도 `dev`·`test`는 확인되지 않았다. ([HF split API][hf-splits])

### 필드와 정답 매핑

| 필드        | 실제 자료형  | 의미와 구현상 주의점                              |
| ----------- | ------------ | ------------------------------------------------- |
| `id`        | string       | 원본 식별자. **유일 키가 아니다.**                |
| `paragraph` | string       | 배경 지문. 없는 경우 빈 문자열                    |
| `question`  | string       | 질문. 문항 안의 설명·보기·줄바꿈도 포함할 수 있음 |
| `choices`   | list[string] | 선택지 4개 또는 5개. 순서 보존                    |
| `answer`    | string       | 정답 **선택지 내용**. 알파벳이나 번호가 아님      |

현재 1,995행 모두 `answer`와 정확히 같은 선택지가 **하나씩** 있다. 따라서 원본 순서의 정답 인덱스는 `choices.index(answer)`이고, 알파벳 표시는 그 인덱스를 A–E에 대응시킨다. 선택지를 순환 배치할 때는 정답 인덱스도 함께 옮겨야 한다.

### 실제 예시 2개

아래는 구조를 보여 주기 위한 예시다. 두 번째의 긴 지문은 **요약 표시**했으며, 실제 평가에서는 원문 전체를 입력해야 한다. 행 번호는 해당 JSON 배열의 0-based 인덱스다.

**문화·4지선다·지문 없음:** `Culture/Korean Economy/Economy_KIIP.json#0`. ([원본][example-culture])

```text
id: KIIP_economy_1
paragraph: ""
question: 다음은 한국 사회의 경제에 대한 문제이다.
          한국이 외환위기를 완전히 극복한 년도는 언제인가?
choices: ["1999년", "2000년", "2001년", "2002년"]
answer: "2001년"
정답 인덱스: 2 → C
```

**언어·5지선다·지문 있음:** `Language/Textual/Textual_CSAT.json#8`. ([원본][example-language])

```text
id: CSAT_korean_23_9
paragraph: [요약 표시] 유서의 편찬과 조선 실학자들의 서학 수용을 설명하는 지문.
question: 문맥상 ⓐ~ⓔ와 바꾸어 쓰기에 적절하지 않은 것은?
choices: ["ⓐ : 의거(依據)하여", "ⓑ : 계몽(啓蒙)하는", "ⓒ : 용이(容易)하게",
          "ⓓ : 혼재(混在)되어", "ⓔ : 변경(變更)하여"]
answer: "ⓑ : 계몽(啓蒙)하는"
정답 인덱스: 1 → B
```

중복 ID는 `CSAT_korean_13_11`과 `Kedu_16_1`–`Kedu_16_7`이다. Kedu의 동일 ID는 Grammar와 Functional에서 서로 다른 질문에 사용된다. `CSAT_korean_13_11`의 두 행은 공백을 모두 제거하면 같은 지문·질문·보기·정답을 가진다. 평가 추적 키는 **`revision + 파일 경로 + 파일 내 행 번호`**로 두고 원본 ID를 별도로 기록한다.

## 4. 라이선스와 접근: 라이선스, 약관 동의 필요 여부

- **접근 확인:** HF API에서 `gated: false`이며, 인증 없이 고정 revision의 26개 JSON을 내려받았다.
- **데이터 라이선스:** 확인한 [HF 카드][hf-card]에 `license` 메타데이터가 없고, [저자 저장소][author-tree]에도 별도 LICENSE 파일이나 데이터 사용 조건을 명시한 문구를 찾지 못했다. 조사한 공개 이슈·HF 토론에서도 이를 확정하는 저자 답변은 확인하지 못했다. **공개 다운로드 가능 여부와 이용 허락의 범위는 구분한다.**
- **논문 라이선스:** ACL 출판본 첫 페이지는 **CC BY-NC 4.0**, arXiv v2 페이지는 **CC BY 4.0**으로 표기되어 있다. 이 표기를 데이터셋 라이선스로 옮기지 않는다. ([출판본][pdf], [arXiv][arxiv])
- **코드 라이선스:** 하네스·Lighteval의 코드 라이선스 역시 원본 데이터의 이용 조건을 정해 주지는 않는다.

**후속 확인 질문:** 저자에게 데이터셋에 적용할 라이선스와 평가 태스크에서의 이용·출처 표시 조건을 확인할 필요가 있다. 이슈 제안에는 ‘데이터 라이선스 표기 미확인’ 상태를 그대로 적는다. 팀 검토안은 원본 HF 파일을 직접 읽는 방식이며, 가공한 데이터셋을 별도로 재배포하는 작업은 포함하지 않는다. 이번 조사에서는 저자에게 메시지를 보내지 않았다.

## 5. 공식 평가 방식: 프롬프트 형식, few-shot 수와 출처, 채점 방식, 정답 추출·정규화, 지표, 논문 수치

### 프롬프트와 반복 평가

논문 §4는 지문이 있는 **Type 1**, 없는 **Type 2** 예시를 제시한다. Type 2의 한국어 지시문은 다음과 같다. 전체 원문과 입력 배치는 [출판본 p.3339][pdf]에서 확인할 수 있다.

> 주어진 질문을 천천히 읽고, 적절한 정답을 A, B, C, D 중에 골라 알파벳 하나로 답하시오.

지문이 있으면 질문 앞에 배경 지문을 넣으며, 보기와 정답 접두사가 이어진다. 예시에는 4개 보기가 있지만 실제 데이터의 5지선다도 지원해야 한다.

논문은 같은 문항을 **지시문 표현 3가지**로 제시하고, 각 표현마다 **맨 앞의 보기를 맨 뒤로 옮겨 가며, 각 보기가 모든 위치에 한 번씩 오도록 반복 평가**한다. 이 방법을 ‘순환 배치(cyclic permutation)’라고 한다. Type 1·2는 지문 유무에 따른 형식 구분이며, 이것을 ‘표현 3가지’로 세지 않는다.

예를 들어 보기가 사과·배·포도·귤이고 정답이 ‘포도’인 설명용 문항이라면, 각 지시문 표현에 대해 다음 네 가지 배치로 평가한다.

| 배치       | A    | B    | C    | D    | 정답 알파벳 |
| ---------- | ---- | ---- | ---- | ---- | ----------- |
| 원래 순서  | 사과 | 배   | 포도 | 귤   | C           |
| 한 칸 이동 | 배   | 포도 | 귤   | 사과 | B           |
| 두 칸 이동 | 포도 | 귤   | 사과 | 배   | A           |
| 세 칸 이동 | 귤   | 사과 | 배   | 포도 | D           |

문제와 보기 내용은 유지하고, 보기의 위치에 맞춰 정답 알파벳도 함께 바꾼다. 4개 보기의 가능한 모든 순열 24가지를 평가하는 것이 아니라, 위와 같은 **4가지 배치**를 사용한다. 5지선다에서는 같은 방식으로 **5가지 배치**를 사용한다.

**사용 이유:** 논문 §4의 *Prompt Types*는 **보기 순서가 모델 응답에 미치는 영향을 줄이기 위해** 이 방식을 적용했다고 명시한다. 예를 들어 모델이 특정 위치의 보기를 선호하면, 같은 문제라도 정답이 놓인 위치에 따라 결과가 달라질 수 있다. 각 보기를 모든 위치에 놓고 평가함으로써, 하나의 보기 순서에만 결과가 좌우되는 영향을 완화하려는 것이다. ([논문 §4, Prompt Types](https://arxiv.org/html/2403.06412v2#S4))

- **확인된 조건:** 선택지가 N개이면 문항당 `3 × N`회 평가한다. 즉, 4지선다는 지시문 표현 3가지 × 보기 배치 4가지 = **12회**, 5지선다는 3가지 × 5가지 = **15회**다. 현재 데이터로 계산하면 4지선다 1,739 × 12 + 5지선다 256 × 15 = **24,708개의 평가 입력/모델**이다. 후보별 로그 확률 계산 횟수와는 다르다. ([논문 §4, 식 (1)][arxiv])
- **미확인 조건:** 논문은 위의 ‘주어진 질문을 천천히 읽고…’와 같은 **지시문을 세 가지 표현으로 바꿔 평가했다**고 설명한다. 그러나 실제로 사용한 **세 지시문의 정확한 원문은 본문·부록·공개 저장소에서 모두 확인하지 못했다.** 또 논문에 함께 적힌 영어 문장을 실제 모델 입력에도 포함했는지, 공백·구분 기호를 어떻게 넣었는지는 공개된 평가 실행 코드가 없어 대조할 수 없다.

### few-shot 수와 출처

**논문:** 확인한 본문·부록에는 **few-shot 사용 여부, shot 수, 예시 문항의 출처·선정 규칙이 명시되어 있지 않다.** 공개된 프롬프트 예시에는 시범 문제·정답이 없어 0-shot 형태로 보이지만, 실제 실험 전체가 0-shot이었다고 확정하지는 않는다. ([논문 §4 및 부록][arxiv])

**lm-evaluation-harness:** CLIcK 태스크는 **기본적으로 0-shot으로 실행되며, 설정하면 few-shot도 지원한다.** 태스크 설정에 `num_fewshot`이 고정되어 있지 않아, 실행 시 shot 수를 지정하지 않으면 하네스 공통 코드가 0을 적용한다. 예를 들어 `--num_fewshot 5`를 지정하면 문제·정답 예시 5개를 평가 문항 앞에 붙인다. ([문화 설정][harness-cul-config], [언어 설정][harness-lang-config], [shot 수 적용 코드][harness-shot-count])

CLIcK에는 실제로 `train` split 하나만 있으며, 하네스는 이를 다음 두 용도로 사용한다.

```yaml
test_split: train     # 평가할 문제의 출처
fewshot_split: train  # few-shot 예시로 사용할 문제·정답의 출처
```

**few-shot용 문항을 미리 별도로 분리해 둔 구조는 아니다.** 실행 중 각 평가 문항에 대해 해당 태스크의 `train` 문항에서 예시 N개를 무작위로 뽑고, **현재 평가하는 문항 자체는 예시에서 제외**한다. 뽑힌 문제·정답을 프롬프트 앞에 붙이며, 예시로 사용된 문항도 전체 평가 대상에는 그대로 남는다. 따라서 `fewshot_split: train`은 예시를 가져올 위치를 지정한 설정이며, 논문에서 few-shot을 사용했다는 근거는 아니다. ([예시 구성 코드][harness-fewshot-context], [샘플링 코드][harness-sampler])

**팀 검토안:** 우선 **0-shot**으로 HF `train` 전체를 평가한다. 입력에 시범 문제·정답을 넣지 않으므로 별도의 few-shot 예시 출처는 필요하지 않다. 이는 팀이 제안하는 구현 조건이며, 논문의 shot 수로 확정된 사실과 구분한다.

### 채점 방식과 정답 추출 및 정규화

**채점 방식: 모델의 답을 어떻게 선택하고 맞았는지 판단하는가**

| 구분 | 모델의 답을 선택하는 방식 | 정오 판정 |
| --- | --- | --- |
| 논문의 공개 모델 | 알파벳과 보기 내용을 합친 답변 문자열의 로그 확률을 비교해 가장 높은 것을 선택 | 선택한 보기가 정답인지 확인 |
| 논문의 API 모델 | 모델이 생성한 답변에서 선택한 보기를 찾아냄 | 찾아낸 보기가 정답인지 확인. 정답이 명확하면 부가 설명도 허용 |
| 현재 하네스 | A–D/E 알파벳 각각의 로그 확률을 비교하는 `multiple_choice` | 선택한 알파벳이 정답 알파벳과 같은지 확인 |

여기서 **‘채점 후보’는 정답을 고르기 위해 로그 확률을 비교하는 답변 문자열**을 뜻한다. 예를 들어 보기가 `A: 서울`, `B: 부산`, `C: 대구`, `D: 인천`이라면, 논문의 공개 모델 평가는 `"A. 서울"`, `"B. 부산"`, `"C. 대구"`, `"D. 인천"`을 비교하고, 현재 하네스는 `"A"`, `"B"`, `"C"`, `"D"`를 비교한다. **확률을 계산하는 문자열이 서로 다르므로, 두 방식을 같은 평가 조건으로 취급하지 않는다.** ([논문 §4][arxiv], [저자의 후보 형식 설명][author-scoring], [하네스 선택지 구성][harness-cul-utils])

저자는 공개 모델에서 **`"{alphabet}. {option_string}"` 전체를 채점하면서도 ‘알파벳 하나로 답하라’는 지시문을 그대로 사용했다**고 확인했다. 따라서 프롬프트의 답변 지시와 실제로 확률을 계산하는 답변 문자열을 구분해야 한다. ([저자의 추가 답변][author-prompt])

**정답 추출: 모델의 응답에서 어떤 보기를 골랐는지 찾아내는 방법**

공개 모델의 확률 비교 방식과 현재 하네스는 점수가 가장 높은 보기를 바로 선택하므로, 생성된 문장에서 정답을 찾아내는 과정이 필요하지 않다. 하네스는 데이터의 `answer`와 같은 내용을 `choices`에서 찾아 정답 알파벳으로 바꾼 뒤, 예측한 알파벳과 비교한다. ([정답 매핑 코드][harness-cul-utils], [정오 판정 코드][harness-metrics])

**API 모델은 문장으로 답할 수 있으므로, 정답 외에 설명이 붙었다고 무조건 오답 처리하지 않는다.** 논문 §4는 알파벳 하나, 보기 내용과 정확히 일치하는 답변, 정답을 명확히 나타내는 문장, 그 뒤에 설명이 붙은 응답을 허용한다. 이 허용 조건에 맞지 않는 응답은 `out-of-option`으로 분류한다. ([논문 §4, Evaluation Methodology][arxiv])

아래는 정답이 `A: 서울`인 문제를 가정해, 허용 기준을 설명하기 위해 만든 예시다.

| 모델 응답 예시 | 추출할 답 | 허용하는 이유 |
| --- | --- | --- |
| `A` | A | 정답 알파벳을 제시 |
| `서울` | A | 정답 보기 내용을 그대로 제시 |
| `정답은 A입니다.` | A | 정답을 명확한 문장으로 표현 |
| `A입니다. 서울은 대한민국의 수도이기 때문입니다.` | A | 정답을 명확히 제시한 뒤 설명을 덧붙임 |

논문에는 위의 허용 원칙이 있지만, **정확한 답변 추출 코드는 공개 자료에서 확인하지 못했다.** `A인지 B인지 모르겠다`처럼 여러 보기를 언급하거나 정답이 모호한 응답에 적용한 세부 처리 규칙도 확정할 수 없다. API 평가를 구현할 때는 어떤 응답에서 어떤 보기를 추출하고 어떤 응답을 판정 불가로 처리할지 정한 뒤, 사례별로 검증해야 한다.

**정답 텍스트 정규화: 비교하기 전에 답변의 표기를 정리하는 방법**

정규화는 답변 앞뒤의 공백을 지우거나, 소문자 알파벳을 대문자로 바꾸거나, 구두점을 정리하는 등의 처리를 뜻한다. **논문과 공개 자료에서는 API 답변에 적용한 구체적인 정규화 규칙을 확인하지 못했다.** 위의 처리는 개념을 설명하는 예시이며, CLIcK의 공식 규칙으로 확인된 사항은 아니다. 문장으로 표현한 정답을 허용한다는 원칙만으로 공백·대소문자·구두점을 어떤 순서와 범위로 처리했는지까지 알 수는 없다.

현재 하네스의 CLIcK은 생성된 답변을 처리하지 않으므로 이러한 답변 텍스트 정규화 단계가 없다. 데이터의 정답을 매핑할 때도 `choices.index(answer)`로 원본 문자열이 일치하는 위치를 찾는다. API 평가용 정규화를 추가한다면 **팀이 선택한 규칙과 논문에서 확인된 원칙을 구분**해 기록해야 한다. ([정답 매핑 코드][harness-cul-utils])

**로그 확률의 길이 정규화는 별개의 개념이다.** 이는 답변 텍스트를 정리하는 것이 아니라, 답변 문자열의 길이를 이용해 점수를 보정하는 처리다.

- **논문의 공개 모델:** 알파벳과 보기 내용을 함께 채점한다는 점은 확인되지만, 로그 확률을 길이로 나누었는지는 확인되지 않았다. 답변 문자열 앞 공백, BOS/EOS·채팅 템플릿 등 실행 세부조건도 미확인 상태다.
- **현재 하네스:** `acc`는 원래 로그 확률이 가장 높은 답을, `acc_norm`은 로그 확률을 **답변 문자열의 문자 수**로 나눈 점수가 가장 높은 답을 사용한다. CLIcK의 비교 문자열은 모두 한 글자 알파벳이므로 `acc`와 `acc_norm`은 같은 예측을 만든다. 이 `norm`은 공백·대소문자를 정리한다는 뜻이 아니다. ([길이 정규화 및 판정 코드][harness-metrics])
- **팀 검토안:** 알파벳과 보기 내용을 합친 문자열을 사용하되 길이 정규화는 적용하지 않는 방식을 제안한다. 이는 **팀의 선택**이며 논문의 설정으로 확정된 사실이 아니다.

### API 모델의 생성 설정과 하네스 비교

논문 §4는 GPT-3.5-turbo와 Claude-2를 평가할 때 **`temperature=0`으로 답변을 생성했다**고 명시한다. 반면 **최대 생성 길이(`max_tokens` 등), `top_p`, 종료 문자열(`stop`)의 구체적인 값은 본문·부록에서 확인하지 못했다.** 이 값들을 임의로 정하거나 당시 API의 기본값을 사용했다고 가정하면, 논문에서 공개한 조건과 팀이 선택한 조건이 섞이므로 구분해 기록해야 한다. ([출판본 p.3339, §4][pdf], [arXiv §4][arxiv])

보고서에서 확인한 하네스의 CLIcK 태스크는 **답변을 생성하는 방식이 아니라 A–D/E 알파벳 각각의 로그 확률을 비교하는 방식**이다. 따라서 논문의 API 평가와 다음 차이가 있다.

| 항목 | 논문의 API 모델 평가 | 하네스의 CLIcK 구현 |
| --- | --- | --- |
| 평가 방식 | 답변을 생성한 뒤 정답을 판정 | 알파벳별 로그 확률이 가장 높은 것을 답으로 선택 |
| `temperature` | **0으로 명시** | 답변 생성에 사용하지 않음 |
| 최대 생성 길이(`max_tokens` 등) | **명시된 값 확인 못 함** | 답변을 생성하지 않으므로 해당 없음 |
| `top_p`·종료 문자열(`stop`) | **명시된 값 확인 못 함** | 답변 생성에 사용하지 않음 |
| 정답 추출 | 생성된 문장에서 선택한 보기를 찾아야 함 | 선택한 알파벳을 정답과 비교하므로 문장 추출 불필요 |

하네스 설정은 `output_type: multiple_choice`이고, 공통 코드는 이를 **`loglikelihood` 요청**으로 처리한다. 확인한 CLIcK 태스크에는 별도의 생성 설정이나 생성된 답변에서 정답을 추출하는 규칙이 없다. ([문화 설정][harness-cul-config], [언어 설정][harness-lang-config], [요청 구성 코드][harness-requests], [알파벳 선택지 구성][harness-cul-utils])

논문의 API 평가를 재현하려면 **답변을 생성하는 평가 방식과 정답 추출 규칙을 별도로 구현**해야 한다. 공개되지 않은 최대 생성 길이 등의 값은 저자에게 확인하거나, 확인 전에는 팀이 선택한 설정임을 명시해야 한다.

### 지표와 논문 수치

논문은 각 문항에서 `정답 횟수 / (3 × 선택지 수)`를 계산한다. 전체 점수를 계산할 때는 **문항별 점수를 먼저 얻고 평균**해야 5지선다에 더 큰 가중치가 붙지 않는다. 팀의 검증 결과에는 문항 평균과 분야별 평균을 구분해 적는다. ([논문 §4, 식 (1)][arxiv])

아래는 [논문 Table 5][pdf]와 [저자 README][author-readme]의 **Average 행을 발췌한 참고값**이다. 현재 팀 모델의 목표 점수나 구현 합격 기준은 아니다.

| 모델                  | Korean Culture | Korean Language |
| --------------------- | -------------: | --------------: |
| Polyglot-Ko 1.3B      |         32.71% |          22.88% |
| Polyglot-Ko 12.8B     |         33.40% |          22.24% |
| LLaMA 13B (표의 이름) |         36.22% |          26.71% |
| GPT-3.5               |         49.30% |          42.32% |
| Claude2               |         51.72% |          45.39% |

**집계 확인이 필요한 부분:** Table 5의 Average를 단순한 분야 macro 평균이라고 설명할 근거는 없다. 문항 수로 가중해도 일부 값은 일치하지 않는다. 예를 들어 GPT-3.5의 언어 분야 점수 53.19·32.62·38.85에 현재 분야별 285·133·232행을 적용하면 **43.86%**, 단순 평균은 **41.55%**로, 표의 **42.32%**와 다르다. 이는 표의 수치를 이용한 재계산이며 원시 평가 결과를 재현한 것이 아니다. 당시 평가 문항과 Average 산식은 저자에게 확인할 항목이다.

### 팀 검토안: 우선 제안할 평가 범위

**0-shot, 한국어 프롬프트 한 표현, 원본 보기 순서, 알파벳과 선택지 내용을 결합한 후보의 loglikelihood 정확도**를 첫 구현 범위로 제안한다. 이는 운영진과 확정한 세부 방식이 아니라 이번 조사에 따른 검토안이다.

- 채점 후보는 저자가 확인한 알파벳·본문 결합 형식을 사용하고, 기본 지표는 길이 정규화 없는 정확도로 제안한다. 길이 정규화 미사용은 **팀 선택**이며 저자의 설정으로 확정된 사실이 아니다.
- 프롬프트의 지시문과 보기 개수는 실제 선택지 수에 맞춰 A–D 또는 A–E로 구성한다. 모든 보기와 원문 지문을 포함하고, 채팅 템플릿은 기본 검증에서 끈다.
- 세 표현 및 순환 배치를 사용하지 않는다는 차이를 이슈와 결과에 명시한다. 이 점수를 논문 Table 5의 직접 재현 결과로 표시하지 않는다.
- 원형 평가의 확장은 완전한 템플릿·실행 조건을 확인한 뒤 논의한다. 생성형 API 평가도 별도 범위로 제안할 수 있다.

### 하네스의 기본 동작

확인한 [문화 설정][harness-cul-config]과 [언어 설정][harness-lang-config]을 기준으로, CLIcK 태스크는 다음과 같이 동작한다. 논문 방식과의 상세 비교 및 응답 예시는 5번에 정리했다.

1. **평가 데이터:** `test_split: train`으로 CLIcK의 유일한 `train` split을 평가에 사용한다. 분야별 태스크는 문항의 `id`를 기준으로 필터링한다. ([문화 필터][harness-cul-utils], [언어 필터][harness-lang-utils])
2. **few-shot 설정과 예시 선정:** 기본은 **0-shot**이며, `--num_fewshot 5`처럼 지정하면 few-shot도 지원한다. `fewshot_split: train`에 따라 해당 태스크의 같은 `train` 문항에서 예시를 무작위로 뽑되, **현재 평가 문항 자체는 제외**한다. 예시용 문항을 미리 별도로 분리해 둔 구조가 아니며, 예시로 사용된 문항도 전체 평가 대상에는 남는다. ([shot 수 적용][harness-shot-count], [예시 구성][harness-fewshot-context], [샘플링][harness-sampler])
3. **평가 요청:** `output_type: multiple_choice`가 공통 코드에서 **`loglikelihood` 요청**으로 처리된다. A–D/E 알파벳 각각의 로그 확률을 계산해 답을 고르므로, 이 CLIcK 태스크에는 답변 생성용 `temperature`·최대 생성 길이 설정이나 생성 문장에서 정답을 추출하는 규칙이 없다. ([요청 구성][harness-requests], [비교할 알파벳 구성][harness-cul-utils])
4. **정답 매핑:** `choices.index(answer)`로 원본 정답 문자열과 일치하는 보기의 위치를 찾고 A–D/E에 대응시킨다. 이때 공백 제거·대소문자 변환 같은 별도의 텍스트 정규화는 하지 않는다. ([정답 매핑][harness-cul-utils])
5. **채점과 집계:** `acc`는 원래 로그 확률이 가장 높은 답의 정오를, `acc_norm`은 로그 확률을 **답변 문자열의 문자 수**로 나눈 점수가 가장 높은 답의 정오를 계산한다. 현재 비교 문자열은 모두 한 글자 알파벳이므로 두 지표는 같은 예측을 만든다. 각 태스크는 문항별 정오를 평균하며, 그룹은 `weight_by_size: true`로 태스크별 문항 수를 반영해 집계한다. ([채점 코드][harness-metrics], [태스크 설정][harness-cul-config], [그룹 집계][harness-group])

**팀 검증 설정:** 하네스가 few-shot도 지원한다는 점과 구분하여, 팀의 비교 평가에서는 조건을 고정하기 위해 `--num_fewshot 0`을 명시한다.

### 확인된 문제점과 논문과의 차이

1. **5지선다의 다섯 번째 보기 누락:** 문화·언어의 `get_context()`는 모두 `opt[0]`–`opt[3]`만 출력한다. `get_choices()`는 CSAT 문항에서 E까지 후보로 제공하므로 입력에 없는 E를 채점할 수 있다. 이 영향은 **256행 전체**이며, 그중 원본 정답이 E인 행은 **49행**이다. 49행이 반드시 오답이 된다는 뜻은 아니다. ([문화 코드][harness-cul-utils], [언어 코드][harness-lang-utils])
2. **논문과 다른 답변 문자열을 채점:** `get_choices()`는 알파벳만 반환하지만, 논문의 공개 모델 평가는 알파벳과 보기 내용을 합친 문자열을 사용했다. 하네스에서도 보기 내용까지 포함하도록 바꾸면 문자열 길이가 달라질 수 있으므로, 현재처럼 `acc`와 `acc_norm`이 같은 예측을 만든다고 보장할 수 없다. ([답변 문자열 구성][harness-cul-utils], [저자의 설명][author-scoring], [하네스 길이 정규화][harness-metrics])
3. **분야 분류 차이:** 실제 원본 1,995행에 하네스 필터를 적용하면 Grammar **233행**, Functional **132행**이다. 원본 폴더 기준은 각각 **232·133행**이다. `Language/Functional/Functional_CSAT.json#82`의 `CSAT_korean_13_11`이 Grammar로 분류된다. 나머지 분야는 일치하며, 파일·행 키 기준으로 전체 누락이나 복수 태스크 배정은 없었다. 원본 분류와 필터 중 어느 것이 의미적으로 옳은지는 별도 검토가 필요하다. ([언어 필터][harness-lang-utils])
4. **논문의 반복 절차 미구현:** 확인한 태스크에는 지시문 표현 3가지를 적용하거나, 보기 순서를 한 칸씩 옮기며 반복 평가하는 코드가 없다. 한 문항을 한 입력으로 평가한다.

**검증 기준 구성안:** 하네스의 소스 revision을 고정한 뒤, 별도 비교용 설정에서 ① 모든 보기 표시, ② 원본 파일별 분야 선택, ③ 알파벳과 보기 내용을 합친 답변 문자열 및 정답 인덱스, ④ 0-shot·단일 표현·원본 순서·길이 정규화를 적용하지 않는 정확도를 명시한다. 기존 하네스 결과와 **보완한 기준 구현의 결과를 구분**해 저장한다. 보완 코드도 수동 기대값과 독립적인 로그 확률 계산으로 검사한 뒤 Lighteval과 비교한다.

- **데이터 연결:** `hf_repo=EunsuKim/CLIcK`, `hf_subset=default`, `evaluation_splits=[train]`을 사용하고, `hf_data_files`로 각 분야의 원본 파일을 지정하는 안이다. Lighteval 설정에 해당 인터페이스가 있다. ID 기반 분류나 별도 데이터 미러가 필요하지 않은지 실제 로딩 단계에서 확인한다. ([설정 정의][task-config])

CLIcK 이슈를 제안한다는 방향은 합의되었지만, 이 보고서는 이슈 초안이나 제출 기록이 아니다. 태스크 코드 구현과 저자·메인테이너에게 연락하는 작업도 이번 산출물에 포함하지 않는다.

## 8. 구현하면서 어려울 것 같은 부분

아래는 첫 구현의 검증 사항과 확장 시 추가로 결정할 조건이다. few-shot·API 생성 평가 관련 항목은 해당 확장을 선택할 때 적용하며, 현재 제안한 0-shot 확률 평가의 필수 구현 범위에 포함하지 않는다.

1. **논문 절차와 최소 구현의 범위 구분:** 0-shot·단일 지시문·원본 보기 순서는 팀 검토안으로 기록한다. 확인하지 못한 지시문 세 가지를 임의로 만들어 ‘공식 재현’이라고 부르지 않는다. 실제 지시문, shot 수, 보기 순서 변경 여부를 버전과 함께 기록한다.
2. **가변 선택지와 긴 지문:** 선택지 수를 ID 문자열로 추정하지 않고 `len(choices)`로 결정한다. 모든 보기가 프롬프트와 확률을 계산할 답변 문자열에 포함되는지, 긴 지문이 잘리지 않는지 검사한다.
3. **식별자·분야 처리:** 중복 ID를 키로 쓰지 않는다. 원본 경로로 분야를 유지하고, 내용이 비슷한 두 행도 기준 평가에서는 그대로 둔다. 정제한 결과를 보고한다면 별도 점수로 표시한다.
4. **답변 문자열과 길이 정규화:** 알파벳과 보기 내용을 합친 문자열 앞의 공백, 프롬프트와 답변 경계의 토큰화, 길이 정규화 여부가 점수에 영향을 줄 수 있다. 실제 문자열과 토큰을 양쪽 도구에서 대조한다. 알파벳만 비교하는 기존 하네스와 달리 보기 내용까지 포함하면 길이가 달라져 `acc`와 `acc_norm`의 예측이 달라질 수 있다. **로그 확률을 길이로 나누는 처리와 공백·대소문자를 정리하는 텍스트 정규화를 구분**하고, 첫 구현안의 길이 정규화 미사용을 명시한다. ([하네스 길이 정규화][harness-metrics])
5. **공통 오류를 놓칠 가능성:** 동일한 오류가 들어간 프롬프트 함수를 두 도구에 복사하면 점수 일치만으로는 검증되지 않는다. 손으로 확인한 입력·정답 사례와 독립적인 조건부 로그 확률 검산을 함께 사용한다.
6. **점수와 데이터 품질의 해석:** 원본 정답 자체의 문제, 평가 코드의 문제, 추론 수치 차이를 구분한다. 모델이 정답과 다르게 답했다는 사실만으로 원본 라벨 오류라고 판단하지 않는다.
7. **few-shot 확장 시 예시 관리:** 하네스처럼 같은 `train`을 평가와 예시에 함께 사용할 경우, 현재 평가 문항을 제외하는 기준과 예시 선정 규칙을 정해야 한다. 중복 ID만으로 동일 문항을 판단하지 않고 파일 경로·행 번호 등으로 예시를 추적한다. 두 도구를 비교할 때는 shot 수와 seed뿐 아니라 **실제로 선택된 예시 목록·순서·정답 표기까지 동일하게 맞춘다.** 예시로 쓰인 문항이 전체 평가 대상에도 남는다는 점을 결과에 기록한다. ([하네스 예시 구성][harness-fewshot-context], [샘플링][harness-sampler])
8. **API 생성 평가 확장 시 별도 검증:** `temperature=0` 외에 확인되지 않은 최대 생성 길이·`top_p`·`stop`은 저자에게 확인하거나 팀이 선택한 값으로 명시한다. 생성 답변에서 정답을 찾는 규칙과 공백·대소문자·구두점의 정규화 규칙을 따로 정한다. 정답 알파벳만 있는 응답, 보기 내용만 있는 응답, 설명이 붙은 응답, 여러 보기를 언급하거나 정답이 모호한 응답에 대해 예상 판정 결과를 만들고 검증한다. 하네스의 현재 로그 확률 평가 결과를 이 생성 평가의 정답 추출 기준으로 사용하지 않는다.

## 9. 검증 계획: 어떤 모델로 어떤 수치와 비교할지

**목표:** 5번의 팀 검토안이 채택되면, **수동 사례·독립 계산 검증 → 하네스와 Lighteval 비교 → 논문 결과와 비교**의 순서로 평가 구현을 검증한다. 두 도구에 같은 오류가 들어 있을 가능성까지 점검하기 위해, 도구 간 점수 일치만을 근거로 삼지 않는다. 아래는 검증 계획이며 **모델 평가는 아직 실행하지 않았다.**

### 사용할 모델과 환경

| 용도 | 모델 | 확인할 내용 |
| --- | --- | --- |
| 도구 간 비교의 주 모델 | `Qwen/Qwen2.5-7B-Instruct` | 같은 조건에서 보완한 하네스와 Lighteval의 입력·점수·예측이 일치하는지 |
| 도구 간 비교의 보조 모델 | `kakaocorp/kanana-1.5-8b-instruct-2505` | 다른 모델·토크나이저에서도 같은 검증을 통과하는지 |
| 논문 결과 비교의 시작 모델 | [`EleutherAI/polyglot-ko-1.3b`][polyglot-1.3b] | 소규모 검증으로 오류를 먼저 찾고, 전체 평가에서 Table 5의 같은 크기 모델과 분야별 점수 비교 |
| 논문 결과 비교의 추가 모델 | [`EleutherAI/polyglot-ko-12.8b`][polyglot-12.8b] | 같은 계열의 다른 크기에서도 전체 평가하고, 논문과의 차이가 특정 모델에 한정되는지 확인 |
| 원인 분석용 선택 모델 | [`EleutherAI/polyglot-ko-5.8b`][polyglot-5.8b] | 1.3B와 12.8B의 결과 차이가 설명되지 않을 때 중간 크기로 추가 조사 |

Qwen2.5와 Kanana는 CLIcK 논문에서 평가한 모델이 아니므로, 이 모델들의 점수를 논문 모델의 점수와 맞추는 것을 검증 목표로 삼지 않는다. **같은 모델을 두 도구에서 실행한 결과끼리 비교**하고, 논문과의 수치 비교에는 **Polyglot-Ko 1.3B와 12.8B 두 모델**을 사용한다. 논문은 같은 계열의 1.3B·3.8B·5.8B·12.8B를 평가했으며, 각 모델은 해당 크기의 논문 결과와 비교한다. 5.8B는 필요할 때 추가하는 선택 범위다. ([논문 Table 4·5][pdf])

두 크기를 사용하는 목적은 논문과의 차이가 특정 모델에서만 나타나는지, 여러 크기에서 공통으로 나타나는지 살펴보는 것이다. 이것만으로 차이의 원인을 확정하지 않는다. 논문 §4.1에서도 모델 크기에 따른 정확도의 유의한 향상을 확인하지 못했으므로, **큰 모델의 점수가 더 높아야 한다는 조건을 합격 기준으로 삼지 않는다.** ([논문 §4.1][arxiv])

환경 기본안은 **H200, 양자화 없는 BF16, 모델을 한 개씩 실행**하는 것이다. 데이터·모델·토크나이저 revision, 하네스·Lighteval 소스 revision, 추론 라이브러리 버전, 정밀도, 최대 입력 길이와 잘림 처리, 배치 크기, seed를 기록한다. 이는 팀의 실행 환경이며 논문의 당시 환경과 동일하다고 가정하지 않는다.

### 1단계: 수동 사례와 독립 계산 검증

1. **데이터·정답 검사:** 26개 파일·1,995행·분야별 수를 확인한다. 각 분야에서 파일 경로·행 번호순으로 최대 10행을 선택하고, 4·5지선다, 지문 유무, 정답 A·E, 중복 ID, 중복 오답 선택지, 분야 분류 차이 문항이 포함되도록 보충한다. 각 사례의 입력 문장, 비교할 답변 문자열 전체, `gold_index`를 손으로 확인한다. 정답은 보기 중 하나와 유일하게 일치해야 하며, 예상하지 못한 불일치는 자동으로 정규화하거나 제외하지 않고 원인을 조사한다.
2. **로그 확률 독립 검산:** 소규모 사례에서 평가 도구의 채점 함수를 그대로 재사용하지 않고, 모델 출력으로 답변 토큰의 조건부 로그 확률 합을 별도로 계산한다. 프롬프트 토큰이 점수에 포함되지 않는지, 답변 앞 공백과 토큰 경계가 같은지, 팀 기본안에서 길이 정규화를 적용하지 않는지 확인한다.
3. **예측·집계 검사:** 답변별 점수에서 가장 높은 보기를 선택하고 정답과 비교하는 과정을 수동 기대값과 대조한다. 문항별 정오가 분야별·전체 정확도로 집계되는지도 확인한다.

### 2단계: 보완한 하네스와 Lighteval 비교

**비교 조건:** 두 도구 모두 **0-shot·한국어 지시문 한 가지·원본 보기 순서·알파벳과 보기 내용을 합친 답변 문자열·길이 정규화 미사용·채팅 템플릿 끔**으로 맞춘다. 하네스는 6번의 보기 누락과 분야 분류를 보완한 비교용 설정을 사용한다. 이 설정 자체도 1단계 검사를 통과해야 한다.

1. **소규모 비교:** Qwen2.5와 Kanana 각각에 대해 같은 문항 목록을 배치 크기 1로 평가한다. 입력 문자열, 토큰 ID와 경계, 비교할 답변 문자열, 정답 매핑, 답변별 로그 확률, 예측 알파벳, 문항별 정오를 대조한다.
2. **전체 비교:** 소규모 검사와 아래의 수치 허용 범위 설정을 마치면 두 모델 각각에서 11개 분야 전체 1,995행으로 확장한다. 분야별 정확도, 문화·언어별 문항 평균, 전체 문항 평균, 11개 분야 macro 평균을 구분해 기록한다. 실제 평가 건수와 제외·잘림 여부도 남긴다.
3. **불일치 분석:** 문항 키, 양쪽 예측과 정오, 답변별 로그 확률, 상위 두 답의 점수 차이, 입력 토큰 수를 저장한다. 전체·분야별 정확도 차이(%p)와 함께 **예측 불일치 수·비율**을 보고하고, 아래 절차로 모든 불일치 문항을 조사한다. 양쪽이 서로 다른 오답을 선택한 경우도 예측 불일치에 포함한다.

### 도구 간 비교의 오차 기준과 판정 절차

다음은 **같은 모델·데이터·평가 조건을 사용하는 두 구현의 검증 기준**이다. 전체 문항을 평가하더라도 수치 계산이나 구현의 차이는 남을 수 있다. PyTorch도 배치 계산 방식·실행 환경 등에 따라 수학적으로 같은 계산의 부동소수점 결과가 완전히 같지 않을 수 있다고 설명한다. ([PyTorch 수치 정확도 안내][pytorch-numerical])

| 비교 항목 | 목표와 판정 기준 |
| --- | --- |
| 문항 목록·분야·정답 인덱스·입력 문자열·토큰 ID·채점 구간 | **완전 일치**. 차이는 허용 오차로 처리하지 않고 구현·설정을 수정한다. |
| 같은 예측에 대한 정오와 집계 | 문항별 정오·정답 수·분모가 일치해야 한다. 정답 수에서 직접 계산한 정확도와 대조하며 출력 반올림만 구분한다. |
| 답변별 로그 확률 | 비트 단위 일치를 요구하지 않는다. 독립 검산을 통과한 소규모 사례로 수치 허용 범위를 정하고 **전체 평가 전에 고정**한다. 범위를 벗어난 값은 원인을 조사한다. |
| 문항별 예측 답변 | **100% 일치를 목표**로 한다. 모든 불일치 문항을 검토하고, 수치 차이로 설명된 사례와 구현 오류·미해결 사례를 분리한다. |
| 전체·분야별 정확도 | 차이(%p)를 보고하되, 정확도 차이가 작다는 이유만으로 통과시키지 않는다. **설명되지 않은 불일치가 0건**이어야 구현 검증을 완료한다. |

**수치 허용 범위 설정:** 전처리와 독립 검산을 통과한 소규모 문항에서 배치 크기 1과 실제 사용할 배치 크기를 비교하고, 필요한 사례를 FP32 등 더 높은 정밀도로 재계산한다. 답변 길이에 따른 로그 확률 합의 크기와 편차를 확인해, 모델·추론 백엔드·정밀도별로 절대 허용 오차 `atol`과 상대 허용 오차 `rtol`을 정한다. 비교식은 `abs(s_lighteval - s_reference) <= atol + rtol * abs(s_reference)`이며, `s_reference`는 독립 검산으로 확인한 비교 구현의 점수다. 값과 선정 근거를 기록하고 별도 소규모 사례에도 적용한 뒤 전체 평가로 확장한다. **실행 전인 현재는 임의의 숫자를 확정하지 않으며**, 전체 결과를 통과시키기 위해 허용 범위를 사후에 넓히지 않는다. 실행 조건을 바꿔 기준을 다시 정하면 새 검증 조건으로 기록한다.

**예측이 다른 문항의 조사 순서:**

1. 원본 문항과 분야, 입력 문자열·토큰, 답변 문자열, 정답 매핑, 입력 잘림 여부를 다시 대조한다.
2. 배치 크기 1로 재계산하고, 필요하면 더 높은 정밀도와 독립 계산으로 답변별 점수를 확인한다.
3. 상위 두 답의 점수 차이와 실제 수치 편차를 비교한다. 점수가 가깝다는 사실만으로 수치 오차로 단정하지 않고, 재계산 결과가 그 설명을 뒷받침하는지 확인한다.
4. 원인, 영향을 받은 문항·분야, 정확도 변화, 재계산 결과를 남긴다. 확인된 수치 차이에 따른 불일치는 별도로 보고하고, 구현 오류를 수정한 뒤 해당 범위와 집계를 재검증한다. 미해결 사례는 검증 완료로 표시하지 않는다.

**정확도만 비교하면 놓치는 경우:** 한 문항을 한 번 평가하는 최소 구현에서 1,995문항 중 정오 한 개가 바뀌면 전체 문항 평균은 `100 / 1,995 ≈ 0.0501%p`, 20개가 같은 방향으로 바뀌면 약 `1.0025%p` 달라진다. 반대로 한쪽이 맞힌 10개를 다른 쪽이 틀리고, 다른 10개에서 그 반대가 되면 **정확도 차이는 0%p여도 최소 20개 문항의 예측이 다르다.** 따라서 “1%p 이내면 통과” 같은 단일 기준을 사용하지 않는다. 이 계산은 단일 평가의 전체 문항 평균에 해당하며, 분야 macro 평균이나 논문의 반복 평가 점수에는 그대로 적용하지 않는다.

### 3단계: 논문 결과와 비교

**Polyglot-Ko-1.3B로 먼저 소규모 수동·독립 계산 및 도구 간 검증을 진행하고, 12.8B에서도 같은 검사를 수행한다.** 각 모델이 앞의 오차 기준을 충족하면, **두 모델 모두 보완한 하네스와 Lighteval로 전체 1,995문항을 평가**한다. 이후 Lighteval 결과를 논문 Table 5의 해당 크기 모델과 비교한다. 모델 이름이 같아도 논문 당시의 가중치·토크나이저 revision이 같은지는 별도로 확인해야 한다. 두 모델 카드의 컨텍스트 길이는 2,048토큰이므로, 입력과 답변 문자열이 이 범위를 넘는 문항을 사전에 확인하고 잘림 처리 조건을 기록한다. 논문 당시의 처리 방식이 확인되지 않으면 조건 차이로 남긴다. ([1.3B 모델 카드][polyglot-1.3b], [12.8B 모델 카드][polyglot-12.8b])

논문에서 보고한 비교 대상의 Average는 다음과 같다. **각 모델의 11개 분야 점수도 각각 대조**한다. 다만 5번에서 설명한 것처럼 Average 산식은 확인이 필요하므로, 팀의 문항 평균·분야 macro 평균을 논문의 Average와 같은 집계라고 전제하지 않는다. ([논문 Table 5][pdf])

| 논문 모델 | 문화 Average | 언어 Average |
| --- | ---: | ---: |
| Polyglot-Ko 1.3B | 32.71% | 22.88% |
| Polyglot-Ko 12.8B | 33.40% | 22.24% |

논문 비교 실험은 다음 두 경우를 구분해 기록한다.

| 구분 | 실행 및 해석 |
| --- | --- |
| **현재 확인 가능한 조건으로 비교** | Polyglot-Ko 1.3B와 12.8B 각각에 팀의 최소 구현 조건을 적용해 평가한다. 논문 점수와의 차이를 기록하되, 지시문 한 가지·원본 보기 순서·0-shot·길이 정규화 미사용 등 팀이 선택한 조건을 명시한다. 결과는 **조건 차이가 있는 참고 비교**이며 논문 재현 결과로 표시하지 않는다. |
| **논문 조건을 추가 확인한 뒤 재현 점검** | 지시문 세 가지의 원문, shot 수와 예시 선정, 길이 정규화 여부, 모델·토크나이저 revision 및 입력 처리 조건을 확인해 맞춘다. 각 지시문에 보기 순환 배치를 적용하고, 문항별 `정답 횟수 / (3 × 선택지 수)`를 계산한 뒤 분야별로 평균한다. |

두 번째 경우 평가 구현 하나를 기준으로 현재 데이터의 평가 입력은 **모델당 24,708개**, 두 모델 합계 **49,416개**다. 4지선다와 5지선다의 반복 횟수가 다르므로 변형된 입력 전체를 단순 평균하지 않고, **문항별 점수를 먼저 계산**한다. 지시문 원문 등이 확인되지 않으면 임의의 세 표현을 만들어 공식 조건으로 간주하지 않는다. 논문의 전체 절차를 맞추는 실험은 최소 기여 태스크와 별도 설정으로 관리한다. ([논문 §4, 식 (1)][arxiv])

**점수 차이 분석:** 분야마다 논문 점수, 측정 점수, 차이(%p), 문항 수를 기록한다. 프롬프트·보기 배치·shot 수·정규화·정답 및 분야 데이터·입력 잘림·집계 방식의 일치 여부를 함께 정리한다. 조건을 바꾸어 원인을 확인할 때는 한 번에 하나씩 바꾸고 변경 전후를 남긴다. 점수가 비슷하다는 이유만으로 구현이 정확하다고 판단하거나, 점수를 맞추기 위해 문항을 임의로 제외하지 않는다.

**논문과의 차이 판정:** 현재는 평가 조건과 집계 산식에 미확인 사항이 있으므로, 논문 점수에 대한 일률적인 허용 범위(예: ±1%p)를 정하지 않는다. 비교 조건을 확인한 뒤 수치 변동, 반복 평가 방식, 논문 표의 반올림 등을 고려해 재현 판단 기준을 정한다. 이는 앞의 **동일 조건에서 두 구현을 비교하는 기준**과 구분한다.

### 통계적 불확실성과 구현 오차의 구분

고정된 전체 1,995문항의 점수와, 그 결과를 더 넓은 한국어 문항의 성능으로 일반화할 때의 불확실성을 구분한다. **신뢰구간이 겹치거나 통계적으로 유의한 차이가 없다는 사실만으로 두 구현이 같다고 판단하지 않는다.**

모델 간 성능 차이의 불확실성을 추가로 분석할 때는, 두 평가의 문항별 결과를 같은 문항끼리 짝지어 재표집하는 **paired bootstrap**으로 차이의 95% 신뢰구간을 계산하는 안을 사용한다. 분야 구성과 집계 가중치를 유지하고, 재표집 횟수·seed·구간 계산 방법을 기록한다. 같은 지문을 공유하는 등 문항 간 의존성이 있으면 재표집 단위도 함께 검토한다. 논문의 반복 평가를 적용할 경우에는 한 문항의 12회 또는 15회 결과를 한 묶음으로 유지하며, 이를 독립된 24,708개 문항처럼 취급하지 않는다. ([SciPy bootstrap의 `paired` 설정][scipy-bootstrap])

논문 Table 5의 집계 점수만으로는 저자의 문항별 결과와 paired bootstrap을 수행할 수 없다. 해당 결과를 확보하지 못하면 분야별 점수 차이와 조건 차이를 보고하는 범위로 한정한다. 신뢰구간은 성능 해석을 위한 보조 자료이며, 전처리·채점 오류를 허용하는 근거로 사용하지 않는다.

### 기록할 결과와 완료 기준

- **실행 기록:** 실제 프롬프트 원문과 설정, 데이터·모델·토크나이저·코드 revision, 환경 정보, 고정한 수치 허용 범위와 선정 근거, 문항별 점수·예측, 분야별 및 전체 집계, 불일치 분석을 남긴다. 원래 하네스, 보완한 하네스, Lighteval, 논문 비교용 실험을 구분해 저장한다.
- **구현 검증:** Qwen2.5·Kanana·Polyglot-Ko 1.3B·12.8B 각각에서 전체 1,995문항을 비교한다. 입력 구성·정답 매핑·채점·집계의 오류가 없어야 하며, 수치 허용 범위를 벗어난 값과 모든 예측 불일치의 원인을 확인해야 한다. 완전 일치 여부와 확인된 수치 차이에 따른 예외 건수·영향을 보고하고, **설명되지 않은 불일치 0건**을 완료 조건으로 둔다.
- **논문 비교:** Polyglot-Ko 두 크기 각각의 11개 분야 점수 차이와 조건 일치 여부를 정리해야 비교를 완료한 것으로 본다. **논문과 비교했다는 것과 논문 결과를 재현했다는 것을 구분**하고, 미확인 조건이 남으면 재현 여부도 미확정으로 기록한다. 논문 점수나 통계적 신뢰구간을 곧바로 구현 합격 기준으로 사용하지 않는다.

### 집계 재현

아래 Python 3 표준 라이브러리 코드는 고정 revision의 원본 파일을 읽어 표의 주요 통계와 하네스 분야 분류 차이를 다시 계산한다. 모델·GPU·`datasets` 설치가 필요하지 않다. 하네스의 고정된 두 `utils.py`에서 위에서 검토한 함수 정의만 실행하고, `Dataset.filter()`는 리스트 필터로 대체한다. 원본 JSON을 수정하거나 평가 문항을 제외하지 않는다.

<details>
<summary>전체 데이터 및 하네스 필터 검사 코드</summary>

```python
import ast
import json
import re
from collections import Counter, defaultdict
from urllib.parse import quote
from urllib.request import Request, urlopen

AUTHOR = "38373acdf73a11e9fbf3667747da61021439d7b7"
HF = "d61627859645b5e6edc03fd9f835735d8226fa4e"
HARNESS = "d6de81643928d653435c431bae19945d41d32520"

def read(url):
    request = Request(url, headers={"User-Agent": "CLIcK-analysis"})
    with urlopen(request, timeout=60) as response:
        return response.read()

tree = json.loads(read(
    f"https://api.github.com/repos/rladmstn1714/CLIcK/git/trees/{AUTHOR}?recursive=1"
))
assert not tree.get("truncated", False)
paths = sorted(x["path"] for x in tree["tree"]
               if x["type"] == "blob" and x["path"].endswith(".json"))
records = []
for path in paths:
    encoded = quote(path, safe="/")
    hf_bytes = read(f"https://huggingface.co/datasets/EunsuKim/CLIcK/resolve/{HF}/{encoded}")
    author_bytes = read(f"https://raw.githubusercontent.com/rladmstn1714/CLIcK/{AUTHOR}/{encoded}")
    assert hf_bytes == author_bytes, path
    for index, row in enumerate(json.loads(hf_bytes)):
        records.append((f"{path}#{index}", path.split("/")[2], row))

rows = [row for _, _, row in records]
print("files / rows:", len(paths), len(rows))
print("choices:", Counter(len(r["choices"]) for r in rows))
print("source:", Counter(r["id"].split("_")[0] for r in rows))
for category in sorted({cat for _, cat, _ in records}):
    group = [r for _, cat, r in records if cat == category]
    print(category, len(group), Counter(len(r["choices"]) for r in group),
          "paragraph:", sum(bool(r["paragraph"].strip()) for r in group))
ids = Counter(r["id"] for r in rows)
print("unique IDs / duplicate IDs:", len(ids), {k: n for k, n in ids.items() if n > 1})
print("empty questions:", sum(not r["question"].strip() for r in rows))
print("empty choices:", sum(any(not c.strip() for c in r["choices"]) for r in rows))
print("answer matches:", Counter(r["choices"].count(r["answer"]) for r in rows))
print("choice element types:", Counter(type(c).__name__ for r in rows for c in r["choices"]))
norm = lambda s: " ".join(s.split())
print("duplicate choices:", [r["id"] for r in rows
      if len(set(map(norm, r["choices"]))) < len(r["choices"])])
for label, normalize in [("collapse whitespace", norm),
                         ("remove whitespace", lambda s: re.sub(r"\s+", "", s))]:
    groups = defaultdict(list)
    for key, _, r in records:
        content = tuple(normalize(s) for s in [r["paragraph"], r["question"], *r["choices"]])
        groups[content].append(key)
    print(label, [keys for keys in groups.values() if len(keys) > 1])
print("5-choice / gold E:", sum(len(r["choices"]) == 5 for r in rows),
      sum(len(r["choices"]) == 5 and r["choices"].index(r["answer"]) == 4 for r in rows))
print("3N inputs:", sum(3 * len(r["choices"]) for r in rows))

class Rows(list):
    def filter(self, predicate):
        return Rows(r for r in self if predicate(r))

mapping = {
    "cul": {"economy": "Korean Economy", "geography": "Korean Geography",
            "history": "Korean History", "law": "Korean Law",
            "politics": "Korean Politics", "kpop": "Korean Popular",
            "society": "Korean Society", "tradition": "Korean Tradition"},
    "lang": {"text": "Textual", "grammar": "Grammar", "function": "Functional"},
}
keys = {id(row): key for key, _, row in records}
assigned = Counter()
for domain, categories in mapping.items():
    source = read(f"https://raw.githubusercontent.com/EleutherAI/lm-evaluation-harness/"
                  f"{HARNESS}/lm_eval/tasks/click/click_{domain}/utils.py").decode()
    parsed = ast.parse(source)
    functions = ast.Module(body=[n for n in parsed.body if isinstance(n, ast.FunctionDef)],
                           type_ignores=[])
    namespace = {"Dataset": Rows, "List": list}
    exec(compile(functions, f"click_{domain}/utils.py", "exec"), namespace)
    for name, category in categories.items():
        actual = namespace[f"extract_{name}"](Rows(rows))
        expected_keys = {key for key, cat, _ in records if cat == category}
        actual_keys = {keys[id(r)] for r in actual}
        assigned.update(actual_keys)
        print("filter", category, "expected / actual:", len(expected_keys), len(actual),
              "missing:", sorted(expected_keys - actual_keys),
              "extra:", sorted(actual_keys - expected_keys))
print("assignments per row:", Counter(assigned[key] for key, _, _ in records))
```

이번 조사에서 확인한 출력은 26개 파일 / 1,995행, 4지선다 1,739행·5지선다 256행, 고유 ID 1,987개, 정답 E 49행, `3N inputs` 24,708개다. 필터 차이는 Functional의 위 1행이 Grammar로 이동하는 경우만 나타나며, 각 행은 한 태스크에 배정된다.
